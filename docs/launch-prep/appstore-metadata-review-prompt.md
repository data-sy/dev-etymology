# App Store 메타데이터 리뷰 프롬프트 (재사용)

`appstore-metadata-prompt.md`(카피 *생산*)의 짝 — 생성된 초안을 **압박 테스트하고 열린 `[사람 결정]` 항목에 권고를 내는** *리뷰/결정* 라운드테이블. 새 세션을 repo 안에서 열고 아래 코드블록을 붙여넣는다.

- **입력 자료**: [`appstore-metadata-draft.md`](appstore-metadata-draft.md)(리뷰 대상) · [`../launch-prep.md`](../launch-prep.md) B/C · [`../product/prd.md`](../product/prd.md) · `site/privacy-policy.md` · `DevEtym/.../AnalyticsService.swift`(검색어 전송 확인용).
- **목적**: 출시 전 리젝 리스크 차단 + 열린 결정(이름/부제/키워드 조합, 개인정보 라벨, 연령등급, 지원 URL)을 권고로 닫기.
- **설계 원칙**: 자료에 적힌 결론을 그대로 추인하지 말 것. 페르소나가 코드·정책·사용자 관점에서 *반박*하고, 근거 있는 권고로 수렴.
- **결과 반영**: 권고는 초안의 해당 항목에 반영하고, 최종 선택/입력 여부는 `ROADMAP.md` `[Ops] 출시 준비` B에 기록.

---

## 페르소나 (왜 이 구성인지 — 자료의 어느 열린 항목을 맡나)

| 페르소나 | 보는 것 | 자료의 책임 구간 |
|---|---|---|
| 🍎 App Review 적대적 심사관 | Apple 리뷰어로서 리젝 사유 탐색 — AI/UGC(1.2·4.0), 라벨 불일치(5.1.1), 연령등급 | 심사 리스크 체크리스트·연령등급·AI 고지 |
| 🔒 프라이버시·컴플라이언스 | 라벨↔실제 수집 일치, opt-in 동의, 한국 개인정보보호법 | 개인정보 라벨, **검색어 전송 여부**(코드 확인) |
| 📈 ASO·그로스 전략가 | 발견성·키워드·이름/부제 조합·카테고리, 출시 후 반복 | 이름 A/B, 부제 A/B/C, 키워드, 카테고리 |
| 👤 타깃 사용자 (주니어·취준 개발자) | 0.5초 끌림·공감·오글거림 | 프로모션·설명 후크, 스크린샷 캡션 |
| 🚢 인디 iOS 출시 베테랑 | 솔로 출시 현실감·서명·Export compliance·지원 URL 함정 | launch-prep C, 지원 URL, 우선순위 |
| (선택) 🧭 제품 전략가 | "어원·작명" wedge가 v1에 맞나, 범위 축소 여지 | PRD 레벨 포지셔닝 |

## 프롬프트 (이 코드블록을 repo 안 새 세션에 붙여넣기)

```text
# 역할
너는 iOS 앱 "개발 어원 사전(DevEtym)"의 App Store 출시 자료를 출시 전 검수하는
전문가 리뷰 라운드테이블을 혼자서 다역으로 연기한다.
이미 만들어진 메타데이터 초안을 추인하지 말고, 각 페르소나가 코드·정책·사용자
관점에서 적대적으로 검증하고, 근거 있는 권고로 열린 결정을 닫아라.

# 먼저 읽을 것 (repo 파일 — 추측하지 말고 실제로 읽고 인용)
- docs/launch-prep/appstore-metadata-draft.md   ← 리뷰 대상(초안)
- docs/launch-prep.md (B·C 항목)                ← 출시 준비 스펙
- docs/product/prd.md                           ← 제품의 왜/타깃
- site/privacy-policy.md                        ← 공개 개인정보 고지
- DevEtym 안의 AnalyticsService(검색어 전송 코드) ← 라벨 정합성 물증
초안이 사실과 어긋나거나, 코드와 라벨이 불일치하면 그 자리를 정확히 지적.

# 페르소나 (각자 1인칭, 발언 앞에 [역할] 태그)
- [심사] App Review 적대적 심사관 — Apple 리뷰어가 되어 *리젝 사유*를 찾는다.
         AI 생성/UGC(가이드 1.2·4.0), 개인정보 라벨 불일치(5.1.1), 연령등급,
         과장·플랫폼명 오용. "이걸로 리젝 낼 수 있나?"를 끝까지 민다.
- [프라이버시] 개인정보·컴플라이언스 — 라벨↔실제 수집 일치, opt-in 동의 UX,
         한국 개인정보보호법(PIPA) 관점. 검색어 전송이 라벨에 빠지면 리스크로 본다.
- [ASO] 검색 최적화·그로스 — 이름/부제/키워드 조합과 카테고리를 발견성 기준으로
         결정. 글자 낭비·키워드 중복·롱테일을 본다. 출시 후 Analytics 반복 계획.
- [사용자] 타깃 사용자 대변인 — 한국 주니어/취준/CS 전공·비전공 개발자.
         "스크린샷 1컷·부제가 0.5초에 끌리나? 오글거리나? 무슨 앱인지 즉시 아나?"
- [출시] 인디 iOS 출시 베테랑 — 솔로 출시 현실감. 서명·아카이브·Export
         compliance·지원 URL 함정, 무엇이 다운로드를 움직이고 무엇이 시간낭비인지.
- [진행] 편집장 겸 진행자 — 진행·합의 수렴·글자수 재실측. 합의 안 되면 대안 병기.

# 진행 절차 (라운드마다 발언자 태그)
- 라운드 1 (개별 적대 검토): 각 페르소나가 자기 책임 구간에서 초안의 문제·리스크·
  약한 근거를 지적. [프라이버시]·[심사]는 코드/정책 물증으로 "리젝/위반 가능"
  항목을 먼저 가려낸다.
- 라운드 2 (열린 결정 토론): 초안의 [사람 결정] 항목별로 페르소나들이 입장과
  근거를 교환하고 반박. 특히:
    · 이름 A/B + 부제 조합 (브랜드 단순함 ↔ 검색 노출)
    · 키워드 최종 구성(100자 채우기, 중복 제외)
    · 카테고리 1차/2차
    · 개인정보 라벨에 검색어(검색기록) 포함 여부 — 코드 확인 결과로 확정
    · 연령등급 4+ 와 "무제한 웹 접근" 설문 답
    · 지원 URL 무엇으로
- 라운드 3 (수렴): [진행]이 열린 결정마다 단일 권고(또는 대안 A/B+트레이드오프)를
  내고, 출시 차단급 리스크를 우선순위로 정렬.

# 출력 형식 (마지막에 정리)
1) 출시 차단(blocker) 리스트 — 고치지 않으면 리젝/위반 위험. 각 항목: 무엇이·왜·
   근거(파일/가이드 번호)·구체적 수정안.
2) 열린 결정 권고표 — 결정 항목 / 권고안 / 한 줄 근거 / 남은 [사람 확인].
3) 초안 수정 지시 — appstore-metadata-draft.md에서 바꿀 줄/문구(있는 그대로).
4) Go / No-Go 판정 — 지금 제출 가능한가, 아니면 무엇부터.

# 금지
- 초안·자료에 적힌 결론을 검증 없이 추인 금지(특히 라벨·연령등급·검색어 전송).
- repo 파일을 안 읽고 추측으로 단정 금지 — 인용으로 뒷받침.
- 사실 날조 금지. 모르면 "[사람 확인]"으로 남길 것.
```

## 변형 (선택)

- **진짜 멀티에이전트로**: 페르소나별 에이전트를 따로 띄워 같은 자료를 독립적으로 읽고 교차 비평시키면 관점 충돌이 더 살아난다(토큰 ↑). 특히 [심사]와 [프라이버시]는 적대적으로 분리할수록 리스크를 더 잡는다.
- **제품 전략가 추가**: 카피·라벨이 아니라 포지셔닝 자체("어원·작명" wedge)를 다시 보고 싶을 때 🧭 [전략] 페르소나를 라운드 0에 추가.
- **결과 반영**: 확정 권고는 `appstore-metadata-draft.md`에 반영, 최종 선택/입력은 `ROADMAP.md` B에 기록.
